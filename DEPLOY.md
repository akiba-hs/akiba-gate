# Развёртывание akiba-gate

Ничего из описанного ниже пока не выполнено — это инструкция, а не отчёт.
Порядок важен: каждый шаг проверяем до перехода к следующему.

Исходные данные: сервер `192.168.8.43` (Debian + Coolify, Traefik на 80/443),
роутер VyOS `192.168.8.1`, домен `akiba.space` в Cloudflare, публикация наружу
через белый статический IP с пробросом 80 и 443.

---

## 0. Что подготовить заранее

**Публичный ключ JWT.** На машине, где лежит `JWT_KEY` от auth-service
(`central.akiba.space`):

```bash
openssl rsa -in jwt_key.pem -pubout -out jwt_public.pem
```

Приватный ключ никуда не копируем — шлюзу он не нужен.

**Общий секрет с приложением Nextcloud:**

```bash
openssl rand -base64 32
```

Один и тот же секрет идёт в `NEXTCLOUD_SSO_SECRET` у шлюза и в настройку
`shared_secret` приложения. Им приложение доказывает право обменять
одноразовый код на личность: без него украденный код бесполезен.

**Telegram-ID администратора.** Узнать свой — написать боту `@userinfobot`.
Он идёт в `ADMIN_TELEGRAM_ID`, и это единственный человек, у которого доступ
есть сразу. Всем остальным по умолчанию не доступно ничего: резидент
появляется в админке после первого входа, и доступ ему открывают галочками.

**Служебные учётки:**

- qBittorrent: учётная запись `akiba-gate` (или общая, если отдельной не завести).
- Jellyfin: общая учётка резидентов, например `residents`. **Она обязана быть
  обычным пользователем, а не администратором.** Мастер установки Jellyfin
  делает первую учётку администратором, и переиспользовать её здесь нельзя:
  админ в Jellyfin ставит плагины, то есть выполняет произвольный код на
  машине с медиатекой, а учётка одна на всех резидентов. Заведите отдельную и
  снимите с неё все флаги администрирования. Шлюз дополнительно закрывает
  такие запросы сам (`internal/jellyfin/proxy.go`), но проверка в коде —
  страховка, а не замена правильной настройке.
- Nextcloud: служебная учётка **не нужна**. Резидентов заводит
  приложение-адаптер средствами самого Nextcloud, а пароли шлюз не знает и
  не хранит.

## 1. DNS и проброс портов

В Cloudflare создать `A inside.akiba.space -> <белый IP>` с **выключенным**
оранжевым облаком: при включённом прокси HTTP-01 будет проверяться через
Cloudflare, а не через ваш Traefik, и TLS терминируется не там, где нужно.

На VyOS пробросить порты:

```
set nat destination rule 80 description 'HTTP to akiba server'
set nat destination rule 80 inbound-interface name eth0
set nat destination rule 80 protocol tcp
set nat destination rule 80 destination port 80
set nat destination rule 80 translation address 192.168.8.43
set nat destination rule 443 description 'HTTPS to akiba server'
set nat destination rule 443 inbound-interface name eth0
set nat destination rule 443 protocol tcp
set nat destination rule 443 destination port 443
set nat destination rule 443 translation address 192.168.8.43
commit ; save
```

Проверка: `curl -I http://inside.akiba.space/` снаружи должен доходить до
Traefik (пока — 404, роутеров ещё нет).

## 2. Настройка сервисов

### Jellyfin

Настраивать нечего. Префикс `/jellyfin` снимает шлюз, поэтому «Base URL»
в панели администратора менять **не нужно**, и прямой доступ по
`http://192.168.8.43:8096/` остаётся прежним.

Нужна только общая учётка резидентов — её имя и пароль идут в
`JELLYFIN_USER` и `JELLYFIN_PASSWORD`.

Проверка: `curl -s http://192.168.8.43:8096/System/Info/Public` — должен
вернуться JSON, в котором `LocalAddress` без пути.

### qBittorrent

Настройки → Web UI:

- включить **Bypass authentication for clients in whitelisted IP subnets** —
  только если выбран режим `QBITTORRENT_AUTH_MODE=bypass`;
- при режиме `session` (по умолчанию) ничего отключать не нужно: шлюз логинится
  сам служебной учёткой;
- включить **Reverse proxy support** и вписать адрес контейнера шлюза
  в список доверенных прокси — **только в режиме `session`**.

Язык интерфейса qBittorrent роли не играет: прогресс загрузок спрашивается
через API (`/api/v2/torrents/info`), где имена полей от языка не зависят.

Про режим `bypass` отдельно. В нём qBittorrent должен видеть клиентом сам
шлюз, поэтому шлюз снимает заголовок `X-Forwarded-For`, а в whitelist вносится
**подсеть контейнера шлюза**, а не подсети резидентов. Если включить
«Reverse proxy support» вместе с `bypass`, qBittorrent начнёт брать адрес из
`X-Forwarded-For` и whitelist перестанет соответствовать реальности.

### Nextcloud

Установить приложение-адаптер — оно лежит в `deploy/nextcloud-app/`:

```bash
sudo cp -r deploy/nextcloud-app/akibasso /var/www/html/custom_apps/
sudo chown -R www-data:www-data /var/www/html/custom_apps/akibasso
sudo -u www-data php occ app:enable akibasso
```

Это команды для **официального** образа. В спейсе стоит `linuxserver/nextcloud`,
где пути другие (`occ` в `/app/www/public`, приложения в
`/config/www/nextcloud/apps`, владелец `abc`), и всё это внутри контейнера.
Для него есть готовый скрипт с машины разработчика:

```bash
.local/nextcloud-app.sh deploy   # выложить приложение
.local/nextcloud-app.sh apply    # прописать секрет из env.local и gate_url
.local/nextcloud-app.sh check    # проверить цепочку
```

Настроить его. `gate_url` — адрес шлюза, каким его видит **сам Nextcloud**
(внутренний, не публичный); `shared_secret` — тот же, что в
`NEXTCLOUD_SSO_SECRET`:

```bash
occ config:app:set akibasso gate_url --value="http://192.168.8.82"
occ config:app:set akibasso shared_secret --value="<секрет>"
occ config:app:set akibasso landing_path --value="/apps/files"
```

**Порт в `gate_url` — тот, на котором шлюз действительно слушает.** При
запуске через `.local/run.sh` это 80-й (`LISTEN_ADDR=:80`), поэтому адрес без
порта. Восьмитысячный порт из `PUBLIC_BASE_URL` — это порт роутера снаружи
(WAN 8080 → 192.168.8.82:80), изнутри сети его нет. Когда шлюз переедет в
контейнер рядом с Nextcloud, здесь будет его внутренний адрес и порт 8080.

**Приложение обязано ходить на частный адрес.** Nextcloud такие запросы по
умолчанию запрещает (защита от SSRF), поэтому в `redeem()` для этого
единственного запроса стоит `'nextcloud' => ['allow_local_address' => true]`.
Без него обмен кода падает всегда, с записью
`Host "…" violates local access rules`. Системную настройку
`allow_local_remote_servers` включать не нужно — она снимает запрет со всего
Nextcloud сразу.

Служебный администратор и Provisioning API не нужны: резидентов
заводит само приложение. Брутфорс-защиту отключать тоже не нужно — форма
входа в этой схеме не участвует вовсе.

Подробности — в `deploy/nextcloud-app/README.md`.

## 3. Закрыть прямой доступ к сервисам

**Это не опциональный шаг.** Схема опирается на заголовки `X-Akiba-*`, которые
проставляет Traefik. Если до Nextcloud, Jellyfin или qBittorrent можно
достучаться напрямую по порту, проверку авторизации обходит любой, кто может
отправить HTTP-запрос из локальной сети.

Оставить доступными только 80 и 443 (Traefik). Порты `8081`, `8096`, `9090`
привязать к loopback или закрыть фаерволом хоста.

Отдельно про Jellyfin: пока `8096` открыт в локальной сети, схема даёт
удобство, а не ограничение доступа — медиатеку по-прежнему увидит любой,
кто знает адрес. Это осознанный компромисс, а не недосмотр: закрыть порт
можно в любой момент, `/jellyfin` от этого не пострадает.

## 4. Сборка и запуск шлюза

Образ собирается локально — публикующего workflow в репозитории нет намеренно,
проект пока не выкатывается. В `.github/workflows/ci.yml` лежит только
проверка кода (форматирование, `go vet`, тесты, тесты под `-race`).

```bash
docker build -t ghcr.io/akiba-hs/akiba-gate:latest .
```

Каталог состояния должен принадлежать системному пользователю `nonroot` из distroless:

```bash
sudo install -d -o 65532 -g 65532 /data/akiba-gate
```

Туда же кладём тексты интерфейса. В образ они не вшиты намеренно: весь смысл
файла в том, чтобы править надписи без пересборки. Каталог нужен на запись —
испорченный файл шлюз чинит, записывая обратно последние корректные тексты.

```bash
sudo install -d -o 65532 -g 65532 /data/akiba-gate/i18n
sudo install -o 65532 -g 65532 deploy/i18n.ru.json /data/akiba-gate/i18n/
```

Без этого файла шлюз не стартует — и это осознанно: интерфейс без надписей
хуже, чем внятная ошибка при запуске.

В Coolify создать ресурс типа **Docker Compose**, содержимое — `deploy/compose.yml`.
Переменные окружения заполнить по `.env.example`.

`SOCKS5_PROXY` — один прокси на весь Telegram: через него идут и аватарки с
`t.me`, и сообщения бота на `api.telegram.org`. Если с сервера Telegram
доступен напрямую, оставьте переменную пустой: тогда оба запроса пойдут
напрямую, а портал будет ссылаться на аватарки прямо в `t.me`, не пропуская их
через шлюз.

Проверка: `docker exec` не поможет (в образе нет шелла), поэтому смотрим логи и
`curl http://<ip-контейнера>:8080/healthz` из соседнего контейнера.

Журнал — JSON, по строке на событие. Сообщение (`msg`) на русском, ключи полей
английские, поэтому разбирать его можно как обычно:

```bash
docker logs <контейнер> | jq -r 'select(.level=="ERROR") | "\(.time) \(.msg) \(.error // "")"'
docker logs <контейнер> | jq -r 'select(.user) | "\(.user) \(.msg)"'
```

Полезные ключи: `user`, `username`, `service`, `path`, `status`,
`duration_ms` (число, миллисекунды), `error`, `torrent`.

## 5. Маршруты Traefik

Скопировать `deploy/traefik/akiba.yaml` в `/data/coolify/proxy/dynamic/akiba.yaml`
(или добавить через Coolify: Server → Proxy → Dynamic Configurations). Файл
перечитывается на лету.

Перед этим поправить в нём:

- `certResolver` — имя резолвера в вашей установке Coolify (обычно `letsencrypt`);
- **проверить, что для `inside.akiba.space` и `nextcloud.akiba.space` нет
  других роутеров**, созданных Coolify автоматически. Приоритет по умолчанию
  в Traefik v3 равен длине правила, поэтому чужой роутер того же хоста может
  выиграть у нашего и middleware не применятся — молча, без ошибок. В файле
  приоритеты заданы явно и с запасом, но конфликтующий роутер лучше убрать;
- имена `entryPoints` (`http`/`https` — как названы у вас);
- внутренние адреса в секции `http.services`;
- **подсеть локальной сети в матчерах `ClientIP`** (по умолчанию `192.168.8.0/24`);
- имя docker-сети в `deploy/compose.yml` должно совпадать с сетью Traefik,
  иначе `forwardAuth` не достучится до шлюза.

Про http отдельно. Кука авторизации выставлена `auth-service` без флага
`Secure`, а менять его нельзя. Поэтому открытый http разрешён **только из
локальной сети** (матчер `ClientIP`, появился в Traefik v3), а тот же запрос
из интернета получает редирект на https. Иначе семидневный JWT ходил бы по
публичной сети открытым текстом. Требование «`http://inside.akiba.space/`
работает в локалке» при этом выполняется полностью.

Проверки:

```bash
curl -I https://inside.akiba.space/                      # 200, портал без ссылок
curl -I -H 'Accept: text/html' https://inside.akiba.space/qbittorrent/   # 302 на auth.akiba.space
curl -I https://inside.akiba.space/qbittorrent/          # 401: без Accept: text/html
                                                            # шлюз считает запрос программным
curl -I https://inside.akiba.space/verify                # 403 (закрыт снаружи)
```

Заголовок `Accept` здесь принципиален: браузеру шлюз отвечает редиректом на
вход, а программному клиенту — 401, чтобы фронтенды Jellyfin и qBittorrent не
уходили молча на чужой origin.

## 6. DNS в локальной сети (VyOS)

Чтобы `inside.akiba.space` резолвился в локальный адрес и работал без
интернета. Тонкость: авторитативной делаем **только эту запись**, а не всю зону
— иначе `auth.akiba.space` перестанет резолвиться и вход сломается.

```
set service dns forwarding listen-address 192.168.8.1
set service dns forwarding allow-from 192.168.8.0/24
set service dns forwarding cache-size 100000
set service dns forwarding authoritative-domain inside.akiba.space records a '@' address 192.168.8.43
commit ; save
```

Проверка: `dig @192.168.8.1 inside.akiba.space +short` → `192.168.8.43`,
`dig @192.168.8.1 auth.akiba.space +short` → адреса Cloudflare.

## 7. Проверка сценариев вручную

1. Открыть `https://inside.akiba.space/` в приватном окне — ссылок нет,
   есть кнопка входа.
2. Войти через Telegram — появляются три карточки.
3. Jellyfin — открывается без ввода пароля.
4. qBittorrent — открывается, добавить торрент; в логах шлюза появляются
   строки `резидент поставил торрент на загрузку` (с полями `user` и
   `torrent`) и `воркер загрузок запущен`. В групповом чате — сообщение бота.
5. Дождаться конца загрузки. Добавивший получает от бота личное сообщение
   со звуком, в логах — `резиденту сообщено о завершённой загрузке`, а
   следом `все отслеживаемые загрузки завершены, воркер остановлен`.
   Если бот пишет впервые, а человек ни разу ему не писал, Telegram
   откажет — в логах будет `не удалось сообщить резиденту о завершённой
   загрузке`. Это ожидаемо: чтобы получать такие сообщения, нужно один раз
   нажать Start в диалоге с ботом.
6. Nextcloud — открывается уже авторизованным, без ввода пароля. В журнале
   шлюза: `резидент отправлен на вход в Nextcloud`, затем
   `код входа в Nextcloud обменян`. Аккаунт заводится сам при первом заходе.
7. Смените себе пароль в Nextcloud и нажмите на карточку ещё раз — вход
   обязан работать по-прежнему. Это и есть главное свойство схемы: пароль в
   ней не участвует.
8. Админка (`/admin`) — список резидентов. Снимите кому-нибудь галочку и
   попробуйте открыть сервис от его имени: должно быть 403, сразу, без
   перезапуска шлюза.
9. `http://inside.akiba.space/` из локальной сети — работает без редиректа
   на https. Тот же адрес из интернета — редирект на https.
10. Отключить интернет на роутере: уже вошедший резидент продолжает
   пользоваться сервисами (кука живёт 7 дней), новый войти не сможет —
   Telegram-виджету нужен интернет.

---

## Откат

Удалить `akiba.yaml` из каталога динамической конфигурации — Traefik перестанет
знать о новых маршрутах, сервисы вернутся к прежнему поведению. Контейнер шлюза
можно оставить: без роутеров он никому не мешает. В `/data/akiba-gate/gate.db`
лежит список резидентов и выданные им права; они переживают пересоздание
контейнера. Ни паролей, ни истории торрентов там нет.
