# akibasso — приложение-адаптер для Nextcloud

Минимальный адаптер между Nextcloud и `akiba-gate`. Один маршрут, один
контроллер, ни одной собственной таблицы.

## Что он делает

1. Принимает браузер по адресу `/apps/akibasso/login?code=…`.
2. Обменивает код у шлюза (`POST /nextcloud/redeem`, общий секрет в заголовке).
3. Заводит резидента, если такого ещё нет.
4. Открывает ему сессию средствами самого Nextcloud.
5. Готовит его файловое хранилище: создаёт `<uid>/files` и при первом входе
   копирует скелет. Без этого шага сессия открывается, а «Файлы» отвечают
   `500` — обычный вход делает то же самое в `Session::prepareUserLogin()`,
   и мимо этого пути пропустить его нельзя.

## Чего он не делает

**Не знает пароля резидента.** При создании аккаунта Nextcloud требует
какой-нибудь пароль — генерируется случайный и тут же забывается: он никуда
не сохраняется и никогда не используется для входа.

Отсюда главное свойство: **резидент может задать и менять себе пароль в
Nextcloud как угодно, на вход через портал это не влияет.** Вход идёт по
одноразовому коду, пароль в нём не участвует вовсе.

## Установка и настройка

В спейсе Akiba всё это делает один скрипт с машины разработчика, по SSH:

```bash
.local/nextcloud-app.sh deploy   # выложить код приложения
.local/nextcloud-app.sh apply    # прописать секрет из env.local и gate_url
.local/nextcloud-app.sh check    # проверить цепочку и объяснить, что в журнале
```

Ниже — то же самое руками, если скрипта под рукой нет.

**Пути зависят от образа.** В спейсе стоит `linuxserver/nextcloud`, а не
официальный: `occ` там `/app/www/public/occ`, приложения —
`/config/www/nextcloud/apps`, владелец файлов — `abc`, и всё это внутри
контейнера. Команды с `www-data` и `/var/www/html/custom_apps` написаны для
официального образа; на linuxserver они не сработают.

```bash
# linuxserver-образ, изнутри контейнера
NC=$(docker ps --format '{{.Names}}' | grep '^nextcloud-')
docker cp akibasso "$NC:/config/www/nextcloud/apps/"
docker exec -u abc "$NC" php /app/www/public/occ app:enable akibasso

# официальный образ
sudo cp -r akibasso /var/www/html/custom_apps/
sudo chown -R www-data:www-data /var/www/html/custom_apps/akibasso
sudo -u www-data php occ app:enable akibasso
```

Настройки — три штуки (дальше через `occ`, каким бы он ни был в вашем образе):

```bash
# адрес шлюза, каким его видит сам Nextcloud (не публичный!)
occ config:app:set akibasso gate_url --value="http://192.168.8.82"
# тот же секрет, что в NEXTCLOUD_SSO_SECRET у шлюза
occ config:app:set akibasso shared_secret --value="<секрет>"
# куда попадает человек после входа (по умолчанию /apps/files)
occ config:app:set akibasso landing_path --value="/apps/files/"
```

**Про слэш в `landing_path`.** Он не косметика. На путь без слэша nginx
Nextcloud отвечает `301` и строит абсолютный адрес **без порта**: браузер
уходит на `http://192.168.8.43/apps/files/` и упирается в пустоту, хотя вход
только что отработал. С `/apps/files/` этого перехода нет вовсе.

**Про порт в `gate_url`.** Это адрес и порт, на которых шлюз реально слушает
в локальной сети. При запуске через `.local/run.sh` это 80-й порт
(`LISTEN_ADDR=:80`), то есть `http://192.168.8.82` — без порта. Число 8080
встречается в `PUBLIC_BASE_URL`, но это порт роутера снаружи (WAN 8080 →
192.168.8.82:80); изнутри сети его нет, и запрос упрётся в отказ соединения.

Секрет генерируется так же, как и на стороне шлюза:

```bash
openssl rand -base64 32
```

## Обязательно: разрешить запрос на частный адрес

Nextcloud по умолчанию запрещает своим серверным запросам ходить на частные
адреса — защита от SSRF. Шлюз стоит именно в локальной сети, поэтому обмен
кода упирается в этот запрет и **отказывает всегда**, а в журнале Nextcloud
появляется:

```
akibasso: обмен кода не удался: Host "192.168.8.82" violates local access rules
```

Приложение снимает запрет ровно для своего единственного запроса —
`'nextcloud' => ['allow_local_address' => true]` в опциях клиента
(см. `redeem()` в `SsoController.php`). Адрес там не приходит от посетителя:
его задаёт администратор в `gate_url`, поэтому исключение узкое и безопасное.

Системную настройку `allow_local_remote_servers` включать **не нужно**: она
снимает запрет со всего Nextcloud разом — с федерации, внешних хранилищ и
всего остального.

Если вы выложили приложение старой версии, без этой строки, — обмен кода
будет падать с сообщением выше. Лечится выкладкой свежей версии.

## Обязательно: trusted_proxies

Nextcloud стоит за Traefik, поэтому без этой настройки он видит клиентом
Traefik, а не браузер. Шлюз при этом привязывает код к настоящему адресу
браузера — адреса не сходятся, и **вход отказывает всегда**.

```bash
occ config:system:set trusted_proxies 0 --value="<IP Traefik>"
```

В спейсе это уже сделано: `trusted_proxies 0 = 10.0.2.5` — адрес контейнера
`coolify-proxy` в сети Nextcloud.

Оговорка, которая экономит час поисков: **на порт 9090 Nextcloud отвечает
мимо Traefik**, потому что порт опубликован докером напрямую. На этом пути
`trusted_proxies` ни при чём, и Nextcloud видит настоящий адрес браузера —
это проверено по его же журналу, где для захода с Mac стоит `192.168.8.82`.
Значит при обращении по `192.168.8.43:9090` привязка кода к адресу работает,
и выключать её не нужно.

Симптом, если trusted_proxies всё же понадобится и будет забыт: вход
стабильно не работает, а в журнале шлюза — `обмен кода Nextcloud отклонён`
с расходящимися `client_ip_from_nextcloud` и `remote_addr`.

Второй вариант — выключить привязку по адресу на стороне шлюза
(`NEXTCLOUD_SSO_BIND_IP=false`). Но это снимает одну из двух проверок, и
делать так стоит, только если trusted_proxies настроить нельзя.

## Что эта схема НЕ делает

**Не закрывает доступ к Nextcloud задним числом.** Аккаунт, однажды заведённый,
остаётся, и человек может задать себе пароль и заходить напрямую по адресу
Nextcloud. Галочка `nextcloud` в админке шлюза управляет кнопкой входа и
первичным заведением аккаунта — но не тем, что уже существует.

Если доступ нужно отобрать по-настоящему, отключите резидента в самом
Nextcloud:

```bash
sudo -u www-data php occ user:disable tg<telegram_id>
```

**Не работает с серверным шифрованием файлов.** Вход без пароля не может
расшифровать личный ключ резидента. Если модуль шифрования включён, эта схема
не подойдёт.

## Если вход отказывает

Надпись «Код входа недействителен или истёк» показывает не одна причина, и по
экрану они неразличимы — различает только журнал. Смотреть надо в оба сразу:
журнал Nextcloud и журнал шлюза.

| Что в журнале Nextcloud | Где искать |
|---|---|
| `не настроены gate_url или shared_secret` | настройки приложения, см. выше |
| `violates local access rules` | выложена старая версия приложения, без разрешения на частный адрес |
| `Connection refused` / `timed out` | в `gate_url` не тот адрес или порт |
| `401` от шлюза | секрет разошёлся: сверьте его на обеих сторонах |
| `403` от шлюза | код не тот, чужой браузер или просрочен — смотрите журнал шлюза |
| вход прошёл, «Файлы» отдают `500` | старая версия приложения, без подготовки файлового хранилища |

В журнале шлюза при отказе рядом лежат оба адреса и признак `nonce_present` —
по ним видно, дошла ли кука и сходятся ли адреса браузера.

## Проверка

```bash
.local/nextcloud-app.sh check    # дёргает вход негодным кодом и читает журнал
.local/nextcloud-app.sh logs 20  # последние записи akibasso
```

Руками — то же самое:

```bash
occ app:list | grep akibasso
tail -f "$(occ config:system:get datadirectory)/nextcloud.log" | grep akibasso
```

На выдуманный код правильный итог — `403` от шлюза в журнале Nextcloud: связь
есть, секрет принят, отказано по самому коду. Всё остальное разбирается по
таблице выше.
